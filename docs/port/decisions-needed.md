# 判断をお願いしたい事項

移植を進める中で、**VCL 版と挙動が変わる選択**や**VCL に前例が無い値の決定**が溜まりました。
どれも現状のまま動いていますが、方針としてどちらを採るかはメンテナが決めるべきものです。

各項目に現状・選択肢・私の推奨を書いてあります。**推奨のままでよければ何もしなくて構いません**
(この文書がそのまま「そう決めた」記録になります)。変えたい項目だけ教えてください。

---

## 1. 一括リネームの連鎖・交換を成功させるか (挙動の変更)

**現状**: 一時名 (`~nfren_0001.tmp`) を経由する2段階リネームにしてあり、`a→b, b→c` の連鎖や
`a↔b` の交換が **成功します**。

**VCL 版**: `RenDlg.cpp` の `RenOkActionExecute` は同種の一時名方式 (`$~NFnnnn.~TMP`) を
持っていますが、**重複を検出したときだけ**使います。骨格は実装を単純にするため常に
一時名を経由します (リネーム自体は安価なので実害はない想定)。

| 選択肢 | 内容 |
|---|---|
| **A (推奨)** | 現状のまま。常に一時名経由。連鎖・交換が成功する |
| B | VCL と同じく、重複を検出したときだけ一時名を使う |

**推奨理由**: 結果は A と B で同じ (どちらも連鎖・交換が成功する) で、A の方が経路が1本で
バグが入りにくい。ただし「一時名が残る事故」の可能性は A の方が広い (途中で異常終了した
場合)。ロールバックは実装済みですが、プロセスが強制終了した場合は一時名が残ります。

## 2. ファイルペインの列幅がロケールに依存する問題 (既存の不具合)

**現状**: `str_len_half` (usr_str.cpp:1765) が `AnsiString` に変換したバイト長で全角/半角を
判定しています。ACP=932 なら正しいですが、**英語版 Windows では全角文字が1と数えられ、
列幅がずれます**。C++Builder 版から引き継いだ挙動で、移植で持ち込んだものではありません。

| 選択肢 | 内容 | 影響 |
|---|---|---|
| **A (推奨)** | 現状のまま記録に留める | 日本語環境では問題なし。海外ユーザーには表示崩れ |
| B | 幅の判定を East Asian Width ベースに置き換える | ロケール非依存になるが、**既存の表示と1文字単位でずれる可能性**がある |
| C | 実行ファイルのマニフェストに `activeCodePage` を指定してプロセスの ACP を固定する | Windows 11 / Server 2025 以降のみ。古い Windows では効かない |

**推奨理由**: 本フォークの利用者は日本語環境が前提で、B は表示の互換性を崩すリスクが
あります。ただし「OSS として公開して海外から使われる」ことを重視するなら B。

## 3. `msgbox_*` (確認ダイアログ) を wx へ移植するか

**現状**: `src/usr_msg_dlg.cpp` (VCL の `CreateMessageDialog` 依存) は未移植で、
`gui/` 側で個別に `wxMessageBox` / `wxMessageDialog` を出しています。
文言テーブル (`LoadUsrMsg`) は移植済みなので、**メッセージの文言は本物**です。

| 選択肢 | 内容 |
|---|---|
| **A (推奨)** | 現状のまま。`gui/` 側で個別に wx のダイアログを出す |
| B | `usr_msg_dlg.cpp` 相当を wx で実装し、`msgbox_ERR` などの API を復活させる |

**推奨理由**: B は `MainFrm.cpp` などを移植する段階 (Phase 3) で必要になります。今の段階では
呼び出し側が `gui/` だけなので、A で十分です。Phase 3 に入る前に B へ切り替えるのが自然です。

## 4. 画像の読み込みを非同期にするか

**現状**: 同期デコード。2億ピクセルを超える画像は**デコード前に**弾きます
(`WIC_get_img_size` はヘッダのみ読むため即座に判定できる)。上限内でも大きな画像では
一瞬待たされます。

**VCL 版**: ワーカースレッド (`TImgViewThread`) で読み込み、上限は設けていません。

| 選択肢 | 内容 |
|---|---|
| **A (推奨)** | 現状のまま (同期 + 上限) |
| B | `std::thread` か `wxThread` で非同期化し、上限を撤廃する |

**推奨理由**: 実用上の体感は A でも十分なはずです (2億ピクセル未満なら数百ミリ秒)。
実機で触って気になるなら B にします。**実際に触った感触を教えていただけると判断できます。**

## 6. `(DWORD)obj` のポインタ縮小キャスト (16箇所) を直すか

**現状**: `TStringList` の `Objects` スロットに 32bit 値を詰めて `(DWORD)obj` で取り出す
書き方が16箇所あります。C++ としては ill-formed で、GCC は `-fpermissive` で降格して
通しています。

| 選択肢 | 内容 |
|---|---|
| **B (推奨に変更)** | `(DWORD)(DWORD_PTR)obj` へ直す (16箇所) |
| A | 現状のまま (`-fpermissive` で通す) |

**推奨理由**: 当初は「A は C++Builder 側に一切影響しない」ことを理由に A を推していました。
§8 でクロスビルドを維持しないと決まったのでその理由が消え、`-fpermissive` を外せる B の方が
良くなりました。clang 系ツールチェイン (llvm-mingw) を追加ターゲットにする道も開きます。
機械的で安全な変更です。

## 7. 未移植ファイルの narrow リテラル (1,200箇所超) をいつ変換するか

**現状**: ビルド対象のファイル (742箇所) は `_T()` へ変換済み。未移植の GUI ファイル
(`MainFrm.cpp` など) には未変換のものが 1,200箇所以上残っています。

| 選択肢 | 内容 |
|---|---|
| **A (推奨)** | ファイルを移植する時点で、そのファイルだけ変換する |
| B | 今すべて変換する |

**推奨理由**: §8 でクロスビルドを維持しないと決まったので「C++Builder 側でしか検証できない」
という当初の理由は消えました。それでも A を推すのは、B は 1,200箇所超の差分になるのに
**ビルド対象外のファイルなので、変換が正しいかを何も検証できない**ためです
(コンパイルもテストも通らない)。移植する時点で変換すれば mingw で検証できます。

## 8. C++Builder 12.1 とのクロスビルド維持 — **決定済み: 維持しない**

2026-08-21 にメンテナが「C++Builder とのクロスビルドを維持するつもりはない」と決定。
これにより**唯一残っていた未検証事項 (BCC64 での再ビルド) が消えた。**

外れた制約と、それによって可能になること:

| これまでの制約 | 決定後 |
|---|---|
| `src/` の変更は標準 C++ のみ。`#ifdef` でツールチェインを分岐させない | mingw-w64 だけを見て書ける |
| `NyanFi.cbproj` を実態に合わせて維持する | 維持不要 |
| 添字プロキシ・`scope_exit` が BCC64 で通るかの確認 | 不要 |
| §6 の `(DWORD)obj` を直すと C++Builder 側に影響する懸念 | 影響しないので自由に直せる |
| §7 の未変換リテラルを「C++Builder 側でしか検証できない」 | mingw で全部検証できる |

`CLAUDE.md` の規約3 をこれに合わせて書き換えた。
